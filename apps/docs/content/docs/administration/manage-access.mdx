---
title: Decide who can do what
description: Manage people, teams, and access levels in TulipFarm. Invite someone, put people into teams, and check why an action is allowed or denied.
---

Access in TulipFarm answers one question: when someone (or something) tries to do a thing, is
it allowed?

Three ideas do all the work.

- **People and apps** are the things that act. A person signing in is one. So is an agent, a
  routine, an integration, or an API token.
- **Levels** say what an actor may do. Every actor holds one or more.
- **Teams** hold people and shared access together, so you set access once instead of per person.

Everything below is on **Operate → Business → People & access**, which admin accounts can reach.

## The three built-in levels

| Level | What it means |
| --- | --- |
| Owner | The account that set the instance up. Reserved, and never removed by a config sync. |
| Admin | Allowed everything, everywhere. |
| Member | The default for an invited person. Can build and run things; cannot touch admin settings. |

A member can chat, build resource types, agents, skills and routines, work with records and
knowledge, approve work, and issue their own API tokens. A member cannot manage secrets, arm kill
switches, read observability, or change who can do what.

<Callout type="info">
  Members are not second-class. Almost everything in
  [Using TulipFarm](/docs/using-tulipfarm) works on a plain member account. That is the point of
  the split.
</Callout>

## Invite someone

<Steps>
  <Step>
    Go to **Operate → Business → People & access**. The **People** tab is shown first, under the
    heading *Who can do what*.
  </Step>
  <Step>
    Choose **Invite someone** and enter their details.
  </Step>
  <Step>
    Pick the level they should hold. Choose **Member** unless they need to administer the
    instance.
  </Step>
  <Step>
    Use **Manage** next to any person later to change their level or turn the account off.
  </Step>
</Steps>

Full walk-through: [Invite your team](/docs/administration/invite-your-team).

## Put people in a team

A team is worth making as soon as two people need the same access. Change the team, and everyone
in it changes with it.

<Steps>
  <Step>
    Open the **Teams** tab and choose **Start a team**.
  </Step>
  <Step>
    Name it and choose **Create team**.
  </Step>
  <Step>
    Choose **Open team**, then **Add** to put people in it.
  </Step>
  <Step>
    Choose **Give this team more access** and pick a level. If none of the levels fit, use
    **None of these fit. Make a new level**.
  </Step>
</Steps>

A team can sit under one parent team, and access from the parent flows down. A team membership can
be given an expiry, which is useful for contractors and for temporary access during an incident.

## Deprecated API names

Older automation may still call the old `group` API names for one release after the Team API
launches. Those calls update the Team model and return a deprecation notice with the Team endpoint
to use instead.

New automation should use Team routes only. Remove the old names before the next release, when the
compatibility aliases are removed.

## Give an agent a team

An agent can be in a team too, and it decides who can open the documents that agent writes.

By default, a document an agent makes can be opened only by the person who asked for it. Put the
agent in a team, and everyone in that team can open it as well. Nobody has to forward anything.
An HR agent in the **HR** team writes reports the whole HR team can read.

<Steps>
  <Step>
    Open the **Agents** tab.
  </Step>
  <Step>
    Find the agent and pick a team, then choose **Add**.
  </Step>
</Steps>

To let one more person in (a manager who is not in HR day to day), give that person the same team
on the **People** tab. Access is checked fresh every time a document is opened, so removing the
agent or the person from the team takes effect immediately.

Only teams that were set up to accept agents are offered. A team authored for people only will not
appear in the list.

<Callout type="warn">
  Being in a team does not let an agent *read* more. An agent can only open the files its caller
  could already open. The team decides who may read what the agent **writes**.
</Callout>

## Check why something is allowed

When access does not behave as expected, do not guess. Ask.

<Steps>
  <Step>
    Open the **Check** tab, headed *Check what someone can do*.
  </Step>
  <Step>
    Fill in **Who**, **Trying to**, and **What**. Use **More precise** to narrow it to one record,
    one field, or one destination.
  </Step>
</Steps>

The answer comes back as allowed or denied, plus the reason: no levels applied, an explicit denial
matched, or nothing granted the action in the first place.

## Why an agent can do less than you

When an agent acts for someone, its access is the **overlap** of two sets of limits: yours, and
the agent's own. Permissions never add up. They only narrow.

```text
    what you may do        what the agent may do
   ┌───────────────┐      ┌───────────────┐
   │               │██████│               │
   │               │██████│               │
   └───────────────┘      └───────────────┘
                     ▲
              only this overlap runs
```

So an agent acting for an admin is still bound by its own limits, and a generous agent acting for
a member is still bound by the member's. If either side denies, the answer is no.

This is why an agent cannot be used as a way around access rules, and why widening an agent does
nothing for a person who was not allowed anyway.

## Things that have no screen yet

Registering a routine, integration, API client, or service is done through
`POST /api/v1/authz/principals`. There is no screen for those today. Agents are the exception:
giving one a team on the **Agents** tab registers it for you.
