---
title: Manage credentials
description: Store, rotate, and delete the API keys and tokens TulipFarm needs — and understand how it keeps them safe.
---

A **credential** is a password for something else: an API key for a model provider, an OAuth
client for Google Workspace, a key for your git host. TulipFarm calls these **secrets**, and it
keeps them encrypted.

You need an admin account for everything on this page.

## What you get at the end

The key is in TulipFarm's encrypted store and everything that needs it can use it — but **nobody
can read the value back**, including you, including the API. That is deliberate.

## Store a secret

<Steps>
  <Step>
    Open **Operate → Business → Secrets**.
  </Step>
  <Step>
    Under **Configure a provider**, choose a built-in provider, or choose **Custom…** to name the
    key yourself.
  </Step>
  <Step>
    Enter the key and the value. A custom integration token might use a key like `stripe-api-key`.
  </Step>
  <Step>
    Choose **Save provider**. TulipFarm encrypts the value before it is written down.
  </Step>
</Steps>

## Replace or delete one

To rotate a value, save a new value under the same key. Anything that uses that key picks up the
new value on its next call — you do not have to change the definition that refers to it.

To remove one, choose **Delete** on its row. Deleting twice is harmless: if the key is already
gone, the store is already in the state you asked for.

## Why you cannot read a value back

Secret values are **write-only**. `GET /api/v1/secrets/status` tells you which keys exist and
whether each one has a value, and that is all it will ever tell you.

<Callout type="warn">
  This means TulipFarm cannot show you a key you have forgotten. If you lose the original, get a
  new one from the provider and save it over the old key.
</Callout>

## How secrets are protected

Values are encrypted with AES-256-GCM before they are stored in PostgreSQL. They are never written
into your soul, so they never reach your git history.

Each value is protected by wrapping key material, and that material is protected by your
`ENCRYPTION_KEY`.

<Callout type="warn">
  **Losing `ENCRYPTION_KEY` can make every stored secret unreadable.** It belongs in your host's
  secret manager or deployment environment, backed up somewhere separate from the database.
</Callout>

## Secrets and boot-time variables are different things

Some values have to exist *before* the app can start, so they cannot live in a store the app has
not opened yet. `ENCRYPTION_KEY`, `JWT_SECRET`, `WEBHOOK_SIGNING_SECRET`, `DATABASE_URL`, and
`SOUL_PATH` are checked at startup and come from the environment.

Everything else — provider keys, integration tokens, git credentials — is a secret, stored after
boot through the screen above.

| Question | Boot-time variables | Secrets |
| --- | --- | --- |
| Where they live | The environment, or `/opt/tulipfarm/.env` | Encrypted in PostgreSQL |
| When they are read | Before the app starts | While it runs |
| Who sets them | Whoever installs the instance | An admin, in the browser |
| Can you read them back | Yes, from the file | No, never |

See [environment variables](/docs/reference/environment-variables) for the full boot-time list.

## Rotating the encryption key itself

Rotating the low-level key material that wraps your secrets is an operator task done against the
running instance, not something you do in the browser. See
[encryption](/docs/security/encryption).
