---
title: Configure LLM providers
description: Add provider credentials, assign models behind each effort preset, and verify fallback behavior.
---

This guide configures the model providers TulipFarm uses for chat, agents, skills, and
routines. This is one of the few setup tasks that is UI-first instead of prompt-first:
provider secrets and model assignments are managed by admins in **Operate**. For how a request
becomes a model, see [Model routing](/docs/administration/how-model-routing-works).

## Outcome

At the end, each effort preset has at least one priced, chat-capable model behind it and TulipFarm can
reload the model service without restarting the app.

<Steps>
  <Step>
    Open **Operate → Business → Secrets**.
  </Step>
  <Step>
    Under **Configure a provider**, choose a provider id:

    | Provider id | UI label | Secret/config keys |
    | --- | --- | --- |
    | `anthropic` | Anthropic | `anthropic-api-key` |
    | `openai` | OpenAI | `openai-api-key` |
    | `azure` | Azure Foundry | `azure-openai-api-key`, `azure-openai-resource-name`, `azure-foundry-endpoint` |
    | `openai-compatible` | OpenAI-compatible | `openai-compatible-api-key`, `openai-compatible-base-url` |
    | `claude-code` | Claude Code (subscription) | `claude-code-oauth-token` |
    | `codex` | Codex (subscription) | `codex-auth-json` |

    The `openai-compatible-api-key` is optional for proxies that do not require one; the
    base URL is required so TulipFarm knows where to send requests.

    The last two run on a Claude or ChatGPT **subscription** rather than an API key, and their
    credential is minted in a terminal instead of copied from a dashboard. See
    [Run on a subscription plan](/docs/administration/run-on-a-subscription).
  </Step>
  <Step>
    Fill the fields and choose **Save provider**. Secret values are encrypted and
    write-only. Non-secret config, such as a base URL or resource name, can be shown back
    on the provider form.
  </Step>
  <Step>
    Open **Operate → Business → Models**. The page has three ordered fallback chains:
    **Fast**, **Balanced**, and **Thorough**. Add one or more provider rows to each chain.

    See [Model routing](/docs/administration/how-model-routing-works) for how effort presets resolve to model profiles.
  </Step>
  <Step>
    Pick a provider and model for each row. Models must resolve to priced,
    chat-capable entries from the LiteLLM catalog. The Models page pins the resolved
    pricing, context window, and capability metadata into the soul.

    provider model ids are accepted as follows:

    - `anthropic` and `openai`: bare ids or provider-prefixed ids.
    - `azure`: `azure_ai/`, `azure/`, or bare deployment ids.
    - `openai-compatible`: bare ids sent to the configured `base_url`.
    - `claude-code`: `opus`, `sonnet`, or `haiku`.
    - `codex`: `gpt-5.6-sol`, `gpt-5.6-terra`, or `gpt-5.6-luna`.

    The two subscription providers are the exception to the LiteLLM rule above: they have no
    catalog price, so their capability metadata comes from a static table instead and their
    turns are reported as unpriced. See
    [Model routing](/docs/administration/how-model-routing-works#subscription-providers).
  </Step>
  <Step>
    Put the preferred provider first. Runtime fallback tries rows in order. A hard
    failure, such as bad credentials, a bad request, a missing model, or cancellation,
    stops the chain immediately. A transient failure, such as rate limit, timeout,
    network error, or a 5xx response, falls through to the next row.
  </Step>
  <Step>
    In **What each effort means**, choose which derived model profile each effort uses. **Auto
    resolves to** is the default for a turn where nobody picks an effort; **Fast**, **Balanced**,
    and **Thorough** control explicit choices. Pointing a preset at a profile that does not exist
    is rejected on save rather than failing later at the first turn that needs it.
  </Step>
  <Step>
    Choose **Save changes**. The Models page writes the `llm` block in `soul.yaml`, commits it,
    and reloads the LLM service live.
  </Step>
</Steps>

## Verify

Start a new chat and ask a simple question. If a chain has multiple providers, temporarily
make the first row return a transient error and confirm the answer comes from the next
row. Do not use invalid credentials for this test: credential failures are hard failures
and intentionally stop fallback.

<Callout type="warn">
If there is no `soul.yaml#llm` configuration, LLM features are disabled. The app does not invent a
model or silently call an unconfigured provider.
</Callout>
