---
title: Configure LLM providers
description: Add provider credentials, choose a model for each effort, test that it answers, and set the embedding model behind Knowledge search.
---

This guide configures the model providers TulipFarm uses for chat, agents, skills, and
routines. This is one of the few setup tasks that is UI-first instead of prompt-first:
provider secrets and model assignments are managed by admins in **Operate**. For how a request
becomes a model, see [Model routing](/docs/administration/how-model-routing-works).

## Outcome

At the end, each effort preset has a priced, chat-capable model behind it, Knowledge has an
embedding model to index against, and TulipFarm can reload the model service without restarting
the app.

<Steps>
  <Step>
    Open **Operate → Business → Secrets**.
  </Step>
  <Step>
    Under **Configure a provider**, choose a provider id:

    | Provider id | UI label | Secret/config keys |
    | --- | --- | --- |
    | `anthropic` | Anthropic | `anthropic-api-key` |
    | `openai` | OpenAI | `openai-api-key` |
    | `azure` | Azure Foundry | `azure-openai-api-key`, `azure-openai-resource-name`, `azure-foundry-endpoint` |
    | `openai-compatible` | OpenAI-compatible | `openai-compatible-api-key`, `openai-compatible-base-url` |
    | `claude-code` | Claude Code (subscription) | `claude-code-oauth-token` |
    | `codex` | Codex (subscription) | `codex-auth-json` |

    The `openai-compatible-api-key` is optional for proxies that do not require one; the
    base URL is required so TulipFarm knows where to send requests.

    The last two run on a Claude or ChatGPT **subscription** rather than an API key, and their
    credential is minted in a terminal instead of copied from a dashboard. See
    [Run on a subscription plan](/docs/administration/run-on-a-subscription).
  </Step>
  <Step>
    Fill the fields and choose **Save provider**. Secret values are encrypted and
    write-only. Non-secret config, such as a base URL or resource name, can be shown back
    on the provider form.
  </Step>
  <Step>
    Open **Operate → Business → Models**. **Chat models** lists the three *effort presets* —
    the named levels of work whoever starts a turn can pick from — with the model behind each
    and what it costs per million tokens.

    See [Model routing](/docs/administration/how-model-routing-works) for how effort presets resolve to model profiles.
  </Step>
  <Step>
    Choose **Change** on an effort. Pick a provider, then type in **Model** to search the catalog.
    Anything your provider accepts works, listed or not.

    provider model identifiers are accepted as follows:

    - `anthropic` and `openai`: bare ids or provider-prefixed ids.
    - `azure`: `azure_ai/`, `azure/`, or bare deployment ids.
    - `openai-compatible`: bare ids sent to the configured `base_url`.
    - `claude-code`: `opus`, `sonnet`, or `haiku`.
    - `codex`: `gpt-5.6-sol`, `gpt-5.6-terra`, or `gpt-5.6-luna`.
  </Step>
  <Step>
    Choose **Test connection**. TulipFarm makes one live call and reports what it proved: what
    the model replied and how long it took, or why it did not answer. Nothing else on this page
    proves a credential works until a real turn needs it.
  </Step>
  <Step>
    Check **Pricing and limits**. Prices, context window and capabilities resolve from the
    LiteLLM catalog and are pinned into the soul.

    A private deployment or a self-hosted endpoint is never in that catalog. Choose **Enter these
    by hand** and type the context window and the two per-million prices, or that model's spend
    stays invisible in Observability.

    The two subscription providers are the exception to the LiteLLM rule above: they have no
    catalog price, so their capability metadata comes from a static table instead and their
    turns are reported as unpriced. See
    [Model routing](/docs/administration/how-model-routing-works#subscription-providers).
  </Step>
  <Step>
    Back in the table, select **Default** on the effort that should run when nobody picks one.
    That choice sets what most turns cost.
  </Step>
  <Step>
    Set an **Embedding model**. It turns Knowledge into vectors so search matches meaning rather
    than wording; until one is set, Knowledge search falls back to keyword matching. Testing an
    embedding model reports the vector width it returned, which you can accept as the width to
    record.

    <Callout type="warn">
      Changing the embedding model or its width leaves existing vectors unmatchable. Re-index
      Knowledge after saving.
    </Callout>
  </Step>
  <Step>
    Open **Advanced** only if you need it. It holds *standby* models — a second model tried when
    the first fails — and per-effort routing overrides.

    Runtime fallback tries standbys in order. A hard failure, such as bad credentials, a bad
    request, a missing model, or cancellation, stops the chain immediately. A transient failure,
    such as rate limit, timeout, network error, or a 5xx response, falls through to the next row.

    **Auto resolves to** names the profile used when nobody picks an effort. Pointing a preset at
    a profile that does not exist is rejected on save rather than failing later at the first turn
    that needs it.
  </Step>
  <Step>
    Choose **Save changes**. The bar at the foot of the page names what is unsaved, and
    **Discard** puts back the config as it was loaded. Saving writes the `llm` block in
    `soul.yaml`, commits it, and reloads the LLM service live.
  </Step>
</Steps>

## Verify

Choose **Test connection** on each effort. A model that answers reports its reply and the round
trip time; one that does not reports why.

Then start a new chat and ask a simple question. To check a standby takes over, temporarily make
the first row return a transient error and confirm the answer comes from the next row. Do not use
invalid credentials for this test: credential failures are hard failures and intentionally stop
fallback.

<Callout type="warn">
If there is no `soul.yaml#llm` configuration, LLM features are disabled. The app does not invent a
model or silently call an unconfigured provider.
</Callout>
