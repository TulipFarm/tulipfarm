A **skill** is a reusable package. It gives an agent task-specific instructions and references
without loading that material into every turn. It can also publish named tools backed by shell,
TypeScript, or Python scripts. Skills follow the agent-skills shape: `SKILL.md` plus optional
references, assets, schemas, and scripts.

A skill is a *what*, not a *who*. You never talk to a skill; an
[agent](/docs/using-tulipfarm/agents) loads one when the task calls for it, and the agent keeps
answering you. A skill grants no authority — it can only ever be followed by an agent that was
already permitted to do the work. See
[How agents and skills differ](/docs/using-tulipfarm/how-agents-and-skills-differ).

## Progressive disclosure

Skills load in layers. The name and description are visible so the agent can decide whether the
skill applies. The `SKILL.md` body is loaded with the `skill` tool when needed. Supporting files (references, schemas, assets, and scripts) are loaded later by calling `skill` again with a `file`
path, only when the skill asks for them.

That keeps normal turns small while still allowing deep instructions for specialized work.

## Built, bundled, or installed

TulipFarm ships bundled forge skills such as `resource-forge`, `agent-forge`, `skill-forge`,
`routine-forge`, `surface-component-forge`, and `onboarding`. Ask `skill-forge` for a skill by
what it does and it searches the official TulipFarm catalog first, then the public skills.sh
catalog, and writes you a new one only when neither has a match. You can also install from a git
repository directly.

The install flow scans a repository, runs **SkillAudit** (the product's own safety review of what
a skill would be allowed to do) and then installs only after operator confirmation. Installed
skills are written to `soul/skills/{name}/` and pinned in `skills-lock.json` with provenance.

Every skill on your instance has an entry in `skills-lock.json` recording where it came from and
which version is installed:

| `sourceType` | Where it came from |
| --- | --- |
| `bundled` | Shipped with TulipFarm and seeded into your soul at startup. |
| `marketplace` | Installed from the official TulipFarm skills catalog. |
| `public` | Installed from any other source, a GitHub repository or git remote. |
| `curated` | Authored on this instance, through chat or the UI. |

Editing a skill makes it yours: the entry is rewritten as `curated`, and TulipFarm stops
refreshing it from wherever it came from.

The complete selected skill directory is preserved. A skill is defined entirely by its
`SKILL.md`. Its frontmatter carries the configuration, including the command declarations and
sandbox-backed tool contracts an executable package needs. No second definition file is written.

## Executable commands

Ask the assistant to build the skill and its tool contract together:

```prompt
Create a reporting Skill with a Python command named generate_report. Give it JSON input and
output, allow a declared CSV file output, and use only the approved shell-ts-python-v1 runtime.
```

Each published command binds a name to a tool contract, an entrypoint inside the skill package, and
an approved runtime profile. The tool contract remains the authority boundary: it declares risk,
mutation behavior, destinations, approvals, timeouts, and retry safety. A skill cannot grant itself
permission.

The initial `shell-ts-python-v1` profile contains Bash, Node with a `tsx` launcher, Python 3,
`curl`, and `jq`. A run cannot install packages. If a command declares an unknown CLI, publication
is blocked until an operator reviews a new runtime image. Google Workspace `gws` is not included.

Execution receives JSON input as an immutable artifact and a fresh ephemeral workspace. Scripts
write `result.json` plus any declared file outputs under `TULIP_OUTPUT_DIR`. Integration
Credentials are injected only through one-use leases after tool authorization. Network access is
denied unless the tool names an allowed destination and the sandbox backend can enforce it.

The local development backend uses a digest-pinned container. Production deliberately refuses that
backend and waits for an attested remote or microVM sandbox. Backend selection is operational
configuration, not a setting shown to normal users.

## SkillAudit is advisory

SkillAudit is an LLM safety review that reports what the skill asks agents to do, suspicious
instructions, and risk level. The audit report is not an authorization boundary: it never installs
a skill and never refuses one. What it does is make sure you see the risk before you decide. A
high-risk report is shown to you and the choice stays yours, and a low-risk report still does not
auto-install. Whether you install from chat or from the skills UI, the audit runs and a human
approves the write. Executable files also pass deterministic package, runtime, tool Broker,
approval, Credential, sandbox, and output gates when applicable.

Use [Install a skill](/docs/using-tulipfarm/install-a-skill) for the install flow.
