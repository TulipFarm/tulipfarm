Chat is the primary interface to TulipFarm. It is where users ask questions, create records, write
knowledge pages, build the soul, and hand work to agents. Every submitted turn becomes a durable
[Run](/docs/using-tulipfarm/runs), so the work continues even if the browser or channel stream drops.

## The default chat harness

A new chat starts with the code-defined `__tulipfarm_default__` harness. This is TulipFarm's
front-desk assistant. It is not a user-created agent, is not shown as a selectable agent, and is not
stored as `AGENT.md` in the soul.

The default harness can answer, search knowledge, create knowledge pages, and create or update
records directly. When the user asks to build the system itself, it loads a forge skill:
`resource-forge`, `agent-forge`, `skill-forge`, `routine-forge`, `surface-component-forge`, or
`onboarding`. That handoff is visible in the transcript, so a build does not look like a hidden
side effect.

## Brand, business, and agents

**TulipFarm** is the product brand. The configured business is the instance-specific identity stored
in `soul.yaml`, such as `businessName` and `businessDescription`; those facts are rendered into the
system prompt. A user-created **agent** is a Soul-defined actor with its own instructions and
metadata. Selecting an agent changes who runs the turn; it does not rename the product or the
business.

## Selecting or handing off to an agent

The web UI can start a turn with a selected agent. A running agent can also move work:

| Tool | Meaning |
| --- | --- |
| `delegate_to_agent` | Starts helper work as a child run while the current agent keeps ownership of the chat. |
| `spawn_subagent` | Starts a one-off helper the agent defines itself, for a single task. No separate chat is created; the helper's instructions, task and answer appear inside the tool step in the trace. |

Delegation is for scoped help. To change the actor responsible for the chat, `@mention` the agent
you want; the chat stays with that agent until a different one is mentioned.

## Choosing effort, not a model

A participant never picks a model. The composer offers an **effort preset** (Auto, Fast, Balanced,
or Thorough) and the deployment maps each one to a [model profile](/docs/administration/how-model-routing-works). Auto is the
default and lets the deployment decide. Picking effort says how much care a question deserves,
which is a judgement the person asking is well placed to make; picking a model would ask them to
know which provider handles their question best, which they are not.

Every finished reply carries a quiet **receipt**: the model that answered, the effort, and how long
the model call took. When Auto answered, the receipt names the level it resolved to (`Auto →
Balanced`) so the choice made on the participant's behalf is visible rather than implied. Cost is
not shown to participants; operators read the full routing decision from the `model.routed` run
event.

When a reply falls short, **Try harder** re-runs the same message one level higher, escalating from
the level the receipt says was actually applied. It is always the participant's choice, TulipFarm
never silently upgrades a turn. See [Model routing](/docs/administration/how-model-routing-works) for how presets resolve,
and [Configure LLM providers](/docs/administration/configure-llm-providers) for the admin side.

## Reading attachments

Use **Attach files** in the chat composer to upload a document or choose a file you already
have access to. Include the question you want answered when you send the message.

Word documents, spreadsheets, presentations and text-based PDFs are converted locally for the
agent to read. You do not need an external conversion account. The extracted content still goes
to the configured model provider when the agent uses it to answer your question.

Opening a Word document or presentation keeps its rich viewer. If that viewer cannot display the
file, a text-and-table preview can show its readable content instead. Spreadsheets use a grid
preview. A limited-preview notice means the display has been shortened; extraction does not
stop at that display limit. Agent reads have their own content limits.

Spreadsheet reading follows the visible sheets, rows and columns. Hidden content is omitted.
Dates, percentages and currency use stored display values. Formulas use their saved results;
reading a spreadsheet does not recalculate it or provide raw values for numerical analysis.
Keep the original workbook when you need to check a calculation.

Presentation reading includes labelled speaker notes. Its text preview follows the readable
content, not the layout of each slide, and does not assign slide numbers to ordinary headings.

PDFs keep their existing viewer. A model that can read PDF pages still receives the original PDF,
not a replacement made from its extracted text. If a PDF needs OCR, which reads text from images,
it is not added to knowledge as a successful partial text result. A compatible model can still
inspect a readable PDF's pages in chat. Password-protected or unreadable PDFs need a readable
replacement.

Conversion is a best-effort reading, not a promise that every part of the source was recovered.
Download the original when you need to check layout or missing content. A document that cannot
be read produces an error rather than being treated as an empty document. There is no automatic
OCR service to read text from scans.

The agent can read only files you can read. Attaching a file does not automatically add it to
[knowledge](/docs/using-tulipfarm/knowledge), the searchable pages agents use across chats.
Adding a file to knowledge is a separate action by its owner.

## Planning work

Plan mode organizes work into rounds and asks for confirmation before execution. It also
understands reusable YAML plans, structured files that give each step its prerequisites.

```prompt
Review this YAML plan, explain the steps and their dependencies, and wait for my confirmation
before running it.
```

Paste the plan with your message, or name its supporting file in an installed skill, a package
of agent instructions and files. After confirmation, an executable plan is saved as a
**routine**, an automation you can run again. Its **run** records what actually happened;
the chat forecast is not a completion receipt. Ordinary written plans continue to work too.

The [YAML plan reference](/docs/reference/yaml-plans) explains the format and its execution limits.

## Feedback and suggestions

Assistant messages support thumbs up and thumbs down feedback. Feedback is stored per user and
rehydrated when the chat is reopened, so product operators can see which answers helped and which
need improvement.

Suggested prompts are drafts. They populate text the user may send, but they never run work on their
own. A run starts only after a user submits a turn or a declared trigger invokes a routine.

## Durable by default

Sending a message creates a [run](/docs/using-tulipfarm/runs) before the agent starts thinking, and
what you watch on screen is that recorded run playing out, not a live feed that exists only while
you look at it.

So stopping an answer really stops the work. It is not just closing the window on something that
carries on regardless. See [Watch a run](/docs/using-tulipfarm/watch-a-run) for what that looks
like.
