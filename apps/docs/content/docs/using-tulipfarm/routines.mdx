A **routine** is repeatable automation. It captures work that should happen the same way each time:
review an expense, classify an inbound event, wait for approval, update records, or hand a task to
an agent. You build routines by chat through `routine-forge`; the generated definition lives in the
[Soul](/docs/using-tulipfarm/what-a-soul-is).

## Triggered into runs

A routine starts a durable [run](/docs/using-tulipfarm/runs). Manual, scheduled, event, webhook, and
agent-triggered paths all normalize into a run with validated input. Editing a routine later does
not rewrite a run already in flight; work proceeds from the definition snapshot pinned at start.

## States and waits

Routine bodies are made of states. States can perform operations, branch, iterate, sleep, inject
context, or wait on durable conditions. A waiting run holds no live process. It is parked in the
datastore until a timer, event, approval, human task, form wait, or child run resumes it.

States emit a permanent journal of entries, actions, retries, waits, and outcomes. The routines UI
and run inspector stream that journal from persisted run events.

## Human gates

A routine state can pause for [approvals](/docs/using-tulipfarm/approvals). The item appears in Inbox and,
when Slack is connected, can also be answered from Slack. Approving wakes the run; denying routes
through the routine's failure handling.

## Hooks and sandboxing

A routine can include hook logic for computations that do not fit cleanly in declarative states.
Hooks run in the same isolated, time-boxed sandbox family as other authored code paths, and are
validated before use.

Use [Build and run a routine](/docs/using-tulipfarm/build-a-routine) for the task flow.
