TulipFarm is built by chatting. You describe the business object, agent, skill, routine,
integration, or surface you need; the assistant gathers the missing details, writes the right definition into
[the soul](/using-tulipfarm/what-a-soul-is), records the change, and reloads the running
system. The files are the result of the chat, not the interface most users edit.

## The front-desk assistant

Normal chat runs through a built-in assistant. It is not one of the named agents in **agents**, and
you never create or configure it. It is simply always there. It is the front desk for the product:
it answers questions, reads and creates [records](/using-tulipfarm/resources), and reads and
creates [knowledge](/using-tulipfarm/knowledge) directly.

When the request changes what the business system is, the default harness loads a forge skill rather
than improvising the build. The handoff appears in the transcript, so the user can see that a
specialized build workflow is now guiding the turn.

## Forges are the build paths

A forge is a bundled skill with a focused authoring workflow. Forges build resource types, agents,
skills, routines, integrations, and surface components. The **Skills** screen shows the exact
bundled set in your release.

Forges build one thing at a time and in dependency order: resource types before agents that use
them, skills before agents that load them, and agents before routines that call them. An integration
forge also reviews provider destinations, credentials, and operations before asking you to approve
publication.

## Soul writes go live immediately

A completed build writes to the [soul](/using-tulipfarm/what-a-soul-is), commits immediately, reloads the soul,
and reconciles live. A new resource type is ready to hold records without restarting; a new agent is
selectable as soon as it is created; a skill is visible to the runtime after it is activated.

Soul changes are direct writes, not Approval-gated work. Runtime actions on data or external systems
can still pause for [approvals](/using-tulipfarm/approvals), but changing the definition store uses git
history as its review record.

## What stays outside chat

Secrets and model provider configuration are business settings. Admins configure them under
**Operate → Business** so API keys, provider endpoints, and model assignments are handled by
purpose-built forms instead of by model-generated text. See
[Configure LLM providers](/administration/configure-llm-providers) and
[Store a secret](/administration/manage-credentials).
