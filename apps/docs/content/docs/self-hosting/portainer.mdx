Portainer deploys TulipFarm as a **Stack**, its name for a Compose file. Nothing in the
file needs changing before it runs.

<Callout type="info">
  There is no TulipFarm entry in Portainer's App Templates list yet. Create a Stack instead;
  it is the same deployment.
</Callout>

## Create the stack

<Steps>

<Step>

### Create the stack

**Stacks → Add stack**, give it the name `tulipfarm`, and choose a build method:

- **Web editor**. Paste the contents of
  `{{SITE_URL}}/docker-compose.yml`.
- **Repository**. Point at `https://github.com/TulipFarm/tulipfarm` with the Compose path
  `docker-compose.yml`. Portainer can then re-pull on a webhook or a schedule.

<Callout type="warn">
  Deploying from the repository tracks whatever is on `main`. For production, paste the file
  into the web editor and pin `TULIPFARM_VERSION` instead, so an upstream commit cannot
  change your stack without you.
</Callout>

</Step>

<Step>

### Add environment variables

In the stack's **Environment variables** section:

| Variable | Value | Why |
| --- | --- | --- |
| `PUBLIC_URL` | `https://tulip.example.com` or `http://<host-ip>:8080` | Optional environment fallback for headless/IaC setup. |
| `POSTGRES_PASSWORD` | a generated password | Replaces the file's `tulipfarm` default. |
| `ENCRYPTION_KEY` | `openssl rand -base64 32` | Recommended, and only effective if set before the first deploy. |
| `HOST_PORT` | `8080` | Change if the port is taken on the host. |

</Step>

<Step>

### Deploy and finish setup

**Deploy the stack**, then wait for the `app` container to report healthy: Portainer reads
the Compose healthcheck, which polls `/readyz`. First boot runs database migrations, so
give it a minute.

After creating the admin account, open **Business → About** and save the public address. Use
`PUBLIC_ORIGINS_LOCKED=true` only when Portainer's environment should remain authoritative.

Open `http://<host>:8080` (or your domain) and create the first admin account through
[the setup wizard](/docs/self-hosting/install#finish-setup).

</Step>

</Steps>

## Volumes

The stack creates `tulipfarm_tulipfarm-postgres`, `tulipfarm_tulipfarm-soul`,
`tulipfarm_tulipfarm-data` and `tulipfarm_tulipfarm-bucket` (Portainer prefixes volume names
with the stack name). All four are visible under **Volumes**.

<Callout type="warn">
  Back up `tulipfarm-data`. It holds the generated `ENCRYPTION_KEY` unless you supplied one,
  and the database stores only ciphertext, losing the volume loses every secret with it.
  `tulipfarm-bucket` holds every uploaded and generated file; back that up too.
</Callout>

## Do not publish Postgres

The Compose file deliberately leaves port `5432` unpublished, which is what makes the
default password safe. Portainer makes publishing a port a two-click operation, don't. If
you need external database access, use a [managed database](/docs/self-hosting/managed-database)
instead.

## Updating

**Stacks → tulipfarm → Update the stack**, with *Re-pull image* enabled. Read
[Updating and rollback](/docs/self-hosting/updating) first. Migrations run on boot and do not
have a down-path.

## Do not scale it

Leave `app`, `worker`, and `integration-worker` at **one replica each**. Portainer's scale
control can corrupt the soul git tree on `app` or duplicate maintenance work on `worker`.
See [Deploy](/docs/self-hosting#what-every-deployment-needs).
