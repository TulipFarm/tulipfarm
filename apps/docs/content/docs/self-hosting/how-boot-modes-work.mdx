---
title: How boot modes work
description: How a fresh TulipFarm instance decides whether to open the setup wizard, seed itself from the environment, or do neither.
---

On an independently hosted installation, TulipFarm first asks: **does an admin
already exist?**

Everything on this page follows from that. There are two ways an instance gets its first admin, and
the instance chooses between them by itself.

Independent hosting is the default. Explicit TulipFarm-hosted configuration is checked before
either setup path can open, as described below.

## The decision

```text
        instance starts
              │
              ▼
      does any user exist? ──── yes ──► normal boot, nothing special
              │
              no
              │
              ▼
   are ADMIN_EMAIL and ADMIN_PASSWORD set?
              │
      ┌───────┴───────┐
     yes              no
      │                │
      ▼                ▼
  headless seed    wizard mode
  (no browser)     (/setup opens)
```

## Wizard mode

This is the default, and it is what a `curl | bash` install and local development both land in,
because neither sets any environment variables.

`GET /api/v1/setup/status` reports `needsSetup: true`, so the web app sends every visitor to
`/setup` until an admin exists.

The wizard only ever creates the **first** admin. The moment one exists it closes, and its step
routes return `403` from then on. It cannot be used to mint a second.

<Callout type="warn">
  Until that first admin exists, `/setup` is unauthenticated. On an instance reachable from the
  internet, **whoever arrives first becomes the admin**. This is why the installer tells you to
  finish setup immediately.
</Callout>

Finishing writes `setupComplete: true` into `soul.yaml`. That marker lives in your soul, which
means it is in git history rather than only in the database.

## Headless mode

This is for deployments where configuration is injected before anything boots: a Kubernetes
manifest, a CI pipeline, a managed platform.

Setting `ADMIN_EMAIL` and `ADMIN_PASSWORD` seeds the first admin without a browser. Adding
`LLM_API_KEY` seeds the model provider too, which produces an instance that is genuinely ready
rather than merely reachable.

In production, admin credentials **without** `LLM_API_KEY` are refused. That refusal is
deliberate: an instance that boots with an admin but no model is one that looks fine and answers
nothing.

Seeding is idempotent. Once any user exists it does nothing, so re-running your deployment is safe.

<Callout type="info">
  Headless seeding handles API-key providers only. A Claude or ChatGPT subscription needs an
  interactive browser sign-in, so those are configured afterwards. See
  [run on a subscription](/docs/administration/run-on-a-subscription).
</Callout>

The step-by-step is in [headless setup](/docs/self-hosting/headless).

## Why the marker lives in two places

Setup state depends on **both** the soul and the database, and they can disagree.

If you restore an old `soul.yaml` that has no `setupComplete` marker, but users already exist in
the database, the instance treats setup as complete. It trusts the users over the marker, because
reopening first-admin creation on a live instance would be a security hole.

The reverse is not survivable. If the database is lost, then users, records, knowledge, runs,
secrets, and identity are all lost, **even if the soul survives perfectly**. The soul holds your
configuration, not your data.

This is the single most important thing to understand before you design a backup:
[back up and restore](/docs/self-hosting/back-up-and-restore) covers what to actually copy.

## Installation identity

Before either setup path opens, TulipFarm records a runtime-installation identity in PostgreSQL.
It identifies this installation, not the business's users or their permissions. The API and both
workers read the same identity on every start; restarting or upgrading does not replace it.

The local business identifier, `BUSINESS_ID`, remains separate. Existing installations keep
their business identifier, accounts, memberships, and history. Two installations using the
default `tulipfarm-local` business identifier still receive different installation identities.
Neither identifier proves global customer ownership or grants access to managed services.

Independent hosting remains the default. This identity adds no cloud login or managed-service
dependency to startup, local login, or supported direct-provider credentials. It does not enroll
the installation in a service, grant remote administration, or provide a migration feature.

Normally, leave `RUNTIME_INSTALLATION_ID` unset or empty. If supplied to the API and workers, it
must be a UUID matching the stored identity; on an uninitialized database it establishes that identity.
A conflicting installation or business identifier stops startup rather than replacing the
stored association. Restore the matching configuration and database instead of deleting the
identity row.

Runtime identity is separate from the anonymous identifier used for product telemetry. This
does not change the [telemetry policy](/docs/security/telemetry).

## Explicit hosted configuration

`RUNTIME_HOSTING_AUTHORITY` identifies who hosts the installation. Leave it unset or empty, or
use `independent`, for supported self-hosting. The value `tulipfarm` explicitly requests TulipFarm
hosting; it does not enroll a business, establish customer ownership, or grant service access.
Any other non-empty value is a configuration error, not a request for the default.

**Production TulipFarm-hosted startup is unavailable in this release.** The authenticated
enrollment and login protocol has not shipped. Selecting `tulipfarm` therefore stops startup,
even with a valid installation UUID. There is no environment switch that supplies trusted
identity verification.

The API and both workers validate the same stored installation, business, and hosting
association before serving requests or starting work. Existing databases retain independent
hosting when upgraded. A conflicting hosting setting cannot change that association. Failed
startup exits without a ready HTTP listener; it does not expose the first-admin wizard, seed
an independent admin account, or start worker loops.

For supported self-hosting, correct an accidental hosted setting to `independent` consistently
on all three processes. For a stored-identity conflict, restore the matching configuration and
database. Do not delete the identity row or change identifiers to bypass the refusal.

Conformance tests can explicitly inject test-only identity verification. A successful
test-hosted assembly keeps independent setup closed, while readiness still checks its database.
That result proves the startup contract, not production hosting, enrollment, login, or outage
recovery. Tests distinguish invalid local configuration from unavailable identity verification;
this release defines no remote-outage or cached-login policy.

Hosting configuration does not relax production execution safeguards. A missing or failing
execution backend does not trigger local or development execution. Existing isolation evidence,
compute and network limits, and controlled credential delivery remain required.

### Configuration ownership

Independent hosting keeps local infrastructure control. **Business → About** can change public
addresses unless `PUBLIC_ORIGINS_LOCKED=true`; **Business → Soul** can manage the configuration
repository's remote. Purchasing model or integration access does not change that ownership.

The test-hosted configuration also checks the ownership boundary: public addresses and repository
controls are marked as managed by the hosting operator. Direct requests and Agent-invoked
repository pushes cannot override that restriction. Saved public addresses and repository
selections do not replace the host's environment configuration. Public web and API addresses
remain separate; callbacks and webhooks use the API address.

Business settings and supported direct model and integration credentials remain available under
their normal permissions. Database and file-storage locations, encryption keys, execution
infrastructure, and official-service endpoints stay deployment configuration, not new customer
settings. A locked control tells you to contact the hosting operator; a failed settings read does
not enable editing. These checks do not enable production hosting or a managed-service connection.
