---
title: Building by chat
description: How TulipFarm turns plain-language requests into live Soul-backed system changes.
---

TulipFarm is built by chatting. You describe the business object, Agent, Skill, Routine, or Surface
you need; the assistant gathers the missing details, writes the right Soul artifact, commits it, and
reloads the live runtime. The files are the result of the chat, not the interface most users edit.

## The default harness

Normal chat runs through the built-in `__tulipfarm_default__` harness. It is not an Agent listed in
**Agents** and it is not an `AGENT.md` file in the Soul. It is the front-desk assistant for the
product: it answers questions, reads and creates [Records](/docs/concepts/resources), and reads and
creates [Knowledge](/docs/concepts/knowledge) directly.

When the request changes what the business system is, the default harness loads a forge Skill rather
than improvising the build. The handoff appears in the transcript, so the user can see that a
specialized build workflow is now guiding the turn.

## Forges are the build paths

A forge is a bundled Skill with a focused authoring workflow. The shipped forge Skills are:

| Forge Skill | Builds |
| --- | --- |
| `resource-forge` | Resource type schemas and optional Resource hooks |
| `agent-forge` | User-created Agents |
| `skill-forge` | Skills and their references |
| `routine-forge` | Routines and their States |
| `surface-component-forge` | Business Surface components |
| `onboarding` | Guided first-run business setup |

Forges build one artifact at a time and in dependency order: Resource types before Agents that use
them, Skills before Agents that load them, and Agents before Routines that call them.

## Soul writes go live immediately

A completed build writes to the [Soul](/docs/concepts/soul), commits immediately, reloads the Soul,
and reconciles live. A new Resource type is ready to hold Records without restarting; a new Agent is
selectable as soon as it is created; a Skill is visible to the runtime after it is activated.

Soul changes are direct writes, not Approval-gated work. Runtime actions on data or external systems
can still pause for [Approvals](/docs/concepts/approvals), but changing the definition store uses git
history as its review record.

## What stays outside chat

Secrets and LLM provider configuration are operator settings. Admins configure them in Settings so
API keys, provider endpoints, and model assignments are handled by purpose-built forms instead of by
model-generated text. See [Configure LLM providers](/docs/guides/configure-llm-providers) and
[Store a secret](/docs/guides/store-a-secret).
