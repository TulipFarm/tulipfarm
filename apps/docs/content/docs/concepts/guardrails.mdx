---
title: Guardrails
description: Input, tool-call, and output guard stages that wrap every turn.
---

Guardrails are policy checks around every turn. They are enforced in the Worker, so a Slack turn and
a web turn pass through the same stages before model input, tool dispatch, and answer persistence.

## Three stages

| Stage | Runs when |
| --- | --- |
| **input** | Before the model sees the user's message |
| **tool-call** | Before a tool call is dispatched |
| **output** | Before the assistant answer is persisted |

A guard returns `pass`, `transform`, or `block`. Transforms feed the changed value to the next guard
in the same stage. The first block short-circuits that stage. Input and output blocks answer with
the guard's message; tool-call blocks return a denial the model can read while the turn continues.

Each guard is bounded by a five-second timeout. A timeout or thrown error is treated as pass and
logged, so a slow or broken guard cannot stall the turn.

## Built-in guards

The shipped guards are pattern-based and do not call an LLM:

| Guard | Stage | Purpose |
| --- | --- | --- |
| `prompt_injection` | input | Blocks common instruction-override phrases. |
| `tool_blocklist` | tool-call | Blocks configured tool names, wildcard matches, or tool categories. |
| `content_filter` | output | Blocks configured sensitive patterns such as credit cards, SSNs, API keys, or email. |

## Policy source

Policy lives in `soul/guardrails.yaml`. The API validates it, ships the resolved policy and digest
with the turn context, and the Worker compiles the same policy before executing. An absent or
invalid config falls back to `DEFAULT_GUARDRAILS`, so the system fails safe and never runs
unguarded.

Admins can view the policy at `/admin/guardrails`. Changes are proposed through
`POST /api/v1/guardrails/changesets`; the read model is `GET /api/v1/guardrails`.
