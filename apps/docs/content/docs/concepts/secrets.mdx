---
title: Secrets
description: Encrypted write-only credential storage for providers, integrations, and operators.
---

A **secret** is encrypted-at-rest credential storage. LLM API keys, integration tokens, Git access
credentials, and custom runtime values are stored as application secrets in Postgres, never as
plaintext in the Soul.

## Bootstrap keys and application secrets

Some values must exist before the app boots: `ENCRYPTION_KEY`, `JWT_SECRET`,
`WEBHOOK_SIGNING_SECRET`, `DATABASE_URL`, and `SOUL_PATH` are validated at startup. Runtime
credentials are stored later through Settings or setup flows and encrypted with AES-256-GCM using
independently wrapped keys.

The `ENCRYPTION_KEY` protects the wrapping key material. Losing it can make application secrets
unreadable, so it belongs in the host's secret manager or deployment environment.

## Write-only values

Secret values are write-only. `GET /api/v1/secrets/status` lists which keys exist and their
metadata, but never returns values. Admins can create, update, or delete a key with the secrets API
or Settings UI.

## Rotation and use

Providers and integrations refer to secret keys by name. Rotating a secret updates what future calls
resolve without changing the Soul definition that references it. Low-level key-encryption rotation
is an operator task, not a browser workflow.

Use [Store a secret](/docs/guides/store-a-secret) for normal secret management and
[Environment variables](/docs/reference/environment-variables) for boot-time variables.
