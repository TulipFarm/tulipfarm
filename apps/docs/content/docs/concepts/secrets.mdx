Secrets are the credentials your instance holds — LLM provider API keys, integration
tokens, and anything else an agent or service needs to authenticate. TulipFarm stores
them in two layers.

## Two layers

- **Bootstrap secrets** are environment variables set before the instance starts:
  `ENCRYPTION_KEY`, `JWT_SECRET`, `WEBHOOK_SIGNING_SECRET`, and the database
  connection. The setup script generates the random ones into `.env.local`.
- **Application secrets** are everything you add at runtime — provider keys and custom
  values. These are encrypted with AES-256-GCM and stored in the datastore, never in
  plaintext and never in the soul.

The `ENCRYPTION_KEY` protects the application secrets. Its length is validated at
startup, so a malformed key fails fast rather than silently corrupting writes.

## Values are write-only

You can store a secret and you can delete it, but you can never read its value back. The
status view lists which keys are set and their metadata — never the values themselves.
Writing secrets is restricted to admins.

## Key rotation without breakage

Changing your `ENCRYPTION_KEY` would normally orphan every secret encrypted under the old
key. TulipFarm avoids that with a dual-key read: set the old key as
`ENCRYPTION_KEY_PREVIOUS` while the new key is `ENCRYPTION_KEY`, and decryption tries the
current key first, then the previous one. Writes always use the current key, so secrets
re-encrypt under the new key as they are touched.

<Callout type="info">
A dedicated rotation endpoint and bulk re-encryption UI are not in V1. The dual-key read
is the supported rotation mechanism — most self-hosted instances rotate rarely.
</Callout>

To add or remove a secret, see [Store a secret](/docs/guides/store-a-secret).
