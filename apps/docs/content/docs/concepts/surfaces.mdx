---
title: Surfaces
description: The Tulip Surface Protocol for structured Artifacts rendered natively per channel.
---

The Tulip Surface Protocol lets Agents emit structured **Artifacts** instead of channel-specific UI
snippets. A Surface Artifact describes intent and interaction contracts once; renderers turn it into
native UI for each delivery target.

## Native renderers

TulipFarm ships renderer packages for several surfaces:

| Package | Renders as |
| --- | --- |
| `@tulipfarm/surface-web` | Trusted React components in the web app |
| `@tulipfarm/surface-slack` | Slack Block Kit |
| `@tulipfarm/surface-github` | GitHub comments and Check Runs |
| `@tulipfarm/surface-telegram` | Telegram message renderer |

Telegram is a renderer package only. TulipFarm does not ship a bundled Telegram integration a user
can connect.

## Interactions post back

Buttons, selects, and other interactions post to `POST /api/v1/surfaces/interactions`. Provider
interactions, such as Slack clicks, are normalized through the internal channel path and resolve to
the same Surface interaction contract as web interactions.

When a Slack interaction resolves, the Slack thread receives the follow-up reply. The interaction
result is therefore part of the same durable channel flow rather than an isolated button callback.

## Catalog and components

`GET /api/v1/surfaces/catalog` returns the component catalog for a resolved presentation target, so
Agents and renderers know what can be shown in that channel. Business-specific Surface components
are authored through the `surface-component-forge` Skill and stored in the Soul with the rest of the
system definition.

Surfaces are not a separate automation engine. They are the structured presentation layer for
Artifacts produced by Runs.
