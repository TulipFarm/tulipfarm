The **Soul** is the definition store for a TulipFarm instance. It is a git repository, created at
`~/.tulipfarm/soul` by default or wherever `SOUL_PATH` points. It holds the business system's shape:
Resource type schemas, Agents, Skills, Routines, Integrations, Surface components, and policy files.

Most users do not edit the Soul directly. They [build by chat](/docs/concepts/building), and the
assistant writes the Soul artifacts underneath.

## Why definitions live in git

Git makes the system definition readable, diffable, portable, and recoverable. A new Agent or
Resource type is a committed change. A remote turns the definition store into a backup. Operators
can inspect history with ordinary git tooling, while everyday users keep working through chat and
Settings.

Records, Knowledge pages, chats, Runs, Approvals, memory, secrets, audit, and identity live in
PostgreSQL, not in the Soul. The Soul defines how the system behaves; the datastore records what
happened and what the business knows.

## Live reconciliation

Soul writes commit immediately and reconcile live. When a tool such as `create_resource_type` writes
`resources/{name}/schema.yml`, the API reloads the Soul and reconciles the datastore without a
restart. Guardrails, LLM config, Routines, Resource types, and other registries reload from the same
`soul.synced` path.

Git backup can be configured during setup or later in Settings. Setting the remote through the UI
syncs immediately. A manual `POST /api/v1/soul/reload` exists for dev-friendly remote-less Souls
when hand-edited files need to be re-read.

## Governance boundary

Soul writes are direct and ungated. Creating an Agent or Resource type changes the definition store
and uses git history as the review record. Runtime work can still pause for
[Approvals](/docs/concepts/approvals), and every turn remains a durable [Run](/docs/concepts/runs).
