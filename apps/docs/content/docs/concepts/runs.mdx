---
title: Runs
description: The durable unit of work behind every chat turn, integration delivery, and routine execution.
---

A **Run** is the durable unit of work in TulipFarm. A chat turn, an integration delivery, and a
Routine execution all become Runs. The API accepts and records the request, but the Worker executes
it; no turn is performed inside the API process that received the browser request.

## Persist first, execute second

Starting work writes the Run, its initial State, and the immutable request Artifact before execution
begins. That is what lets the Worker reconstruct the work after a crash and what lets the UI inspect
work after the original stream is gone.

Run sources describe which executor owns the work: `chat`, `integration`, or `routine`. Invocation
source is separate; it records what accepted the request, such as a web chat, manual trigger,
schedule, or integration webhook.

## Run and State status

Runs move through a small state machine: `queued`, `claimed`, `running`, `waiting`, `succeeded`,
`failed`, `cancelling`, `cancelled`, `attention_required`, and `needs_reconciliation`. Routine
States have their own statuses: `pending`, `ready`, `claimed`, `running`, `waiting`, `succeeded`,
`failed`, `skipped`, `cancelling`, `cancelled`, and `needs_reconciliation`.

`waiting` means the Run is durably parked on a timer, Approval, human task, form wait, event, or
child Run. It does not require a Worker process to stay alive while it waits.

## Event streams survive reconnects

Run events are persisted. `POST /api/v1/chat` streams those persisted events, frame for frame, and
`GET /api/v1/runs/:id/events` exposes the same stream. A dropped connection reattaches by cursor
with `?after=<sequence>` or the `Last-Event-ID` header, so reconnecting resumes after the last event
already seen and avoids duplicates.

The stream is read-only. Losing it never changes the Run, and authorization is rechecked while the
client watches.

## Lifecycle controls

The Run inspector and REST API expose server-authorized controls: cancel, pause, resume, retry, and
reconcile. These controls validate authority on the server; the browser supplies intent, not final
authorization.

Stopping a chat turn cancels the Run answering it through `POST /api/v1/chat/runs/{runId}/stop`.
The Worker holding the Run observes the cancellation and ends the turn with the Run's terminal
status. See [Watch a Run](/docs/guides/watch-a-run) and [Operations](/docs/guides/operations).
