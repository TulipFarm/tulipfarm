<Callout type="warn">
  **There is no official Helm chart and no published Kubernetes manifests.** Nothing is
  hosted at an `oci://` or `https://charts…` URL — any command you find that claims
  otherwise will fail. Kubernetes is not a tested deployment target: CI exercises the
  [Docker Compose](/docs/deploy/docker-compose) stack on every run, and nothing else.

  This page documents the contract the image expects, so you can write manifests you own
  and verify. It is not a supported install path.
</Callout>

If you want a supported deployment today, run the Compose stack on a VM. Kubernetes buys
you little until you need cluster-native secrets, ingress, or managed PostgreSQL, because
TulipFarm does **not** scale horizontally.

## The hard constraint: one replica per workload

Run three workloads from the same image, each with `replicas: 1` and `strategy: Recreate`.
Do not use `RollingUpdate`: it briefly runs two copies and can race the soul worktree or
maintenance consumers.

| Workload | Command | Why it is single-replica |
| --- | --- | --- |
| `app` | default `node server.cjs` | Owns the API, built web UI, soul git worktree, and all database migrations. |
| `worker` | `node worker.cjs` | Executes every turn, wait, outbox loop, cron, and maintenance consumer. Set `WORKER_MAINTENANCE=true` on exactly one copy. |
| `integration-worker` | `node integration-worker.cjs` | Owns Slack and GitHub ingress, sync, delivery, retries, and reconciliation. |

## Workload contract

| Workload | Container port | Probes | Volumes |
| --- | --- | --- | --- |
| `app` | `8080` | `/livez`, `/readyz` | `/opt/tulipfarm/soul` read-write; `/data` read-write. |
| `worker` | `4020` | `/livez`, `/readyz` | `/data` read-only. |
| `integration-worker` | `4030` | `/livez`, `/readyz` | `/data` read-only. |

`/readyz` on `app` checks the datastore. `/readyz` on both workers checks the datastore,
the required schema floor, and whether required consumers are attached. The workers never
migrate; they must start only after `app` has applied migrations and become ready.

Give `app` a generous startup probe on `/readyz`. Migrations run before it listens, so a
fresh database can take minutes on first boot. Without a startup probe, liveness can kill
`app` mid-migration and loop forever.

## Image and storage

| Requirement | Detail |
| --- | --- |
| **Image** | `ghcr.io/tulipfarm/tulipfarm:<tag>` — multi-arch (amd64, arm64). Pin a tag; do not track `latest` in a cluster. |
| **Soul volume** | Mounted only by `app` at `/opt/tulipfarm/soul`. It is a git working tree, not shared application data. |
| **Data volume** | Mounted read-write by `app` and read-only by both workers at `/data`. It holds generated bootstrap secrets and service credentials. |
| **Filesystem group** | The image runs as UID `1000` (`node`). Set `podSecurityContext.fsGroup: 1000` or mounted PVCs may not be writable. |

If your storage class cannot mount the same `/data` volume into all three workloads, supply
`ENCRYPTION_KEY`, `WORKER_API_CREDENTIAL`, and `INTEGRATION_WORKER_API_CREDENTIAL` from
Kubernetes `Secret` objects instead. The Compose path relies on `app` minting those
credentials into `/data` on first boot and the workers reading them back.

## Required environment

| Workload | Variable | Notes |
| --- | --- | --- |
| All | `DATABASE_URL` | PostgreSQL 17 that permits `CREATE EXTENSION vector` and `citext`. See [Managed database](/docs/deploy/managed-database). |
| All | `NODE_ENV` | `production`. |
| `app` | `PORT` | `8080`. |
| `app` | `PUBLIC_URL` | The `https://` origin your Ingress serves. Wrong value means login silently fails. |
| `app` | `SOUL_PATH` | `/opt/tulipfarm/soul`. |
| `app` | `TF_DATA_DIR` | `/data`. |
| `app`, `worker` | `ENCRYPTION_KEY` | Prefer a `Secret`. If unset, `app` generates it in `/data/secrets.env` and `worker` reads it from there. |
| `app` | `JWT_SECRET`, `WEBHOOK_SIGNING_SECRET` | Prefer `Secret` values. |
| `worker` | `WORKER_PORT` | `4020`. |
| `worker` | `WORKER_MAINTENANCE` | `true` on the one worker that owns cron and maintenance consumers. |
| `worker` | `INTERNAL_API_URL` | URL for the `app` Service, for example `http://app:8080`. |
| `worker` | `WORKER_API_CREDENTIAL` | Service credential. If unset, read from `/data/worker.env` after `app` mints it. |
| `worker` | `TF_DATA_DIR` | `/data`. |
| `integration-worker` | `INTEGRATION_WORKER_PORT` | `4030`. |
| `integration-worker` | `INTERNAL_API_URL` | URL for the `app` Service, for example `http://app:8080`. |
| `integration-worker` | `INTEGRATION_WORKER_API_CREDENTIAL` | Service credential. If unset, read from `/data/integration-worker.env` after `app` mints it. |
| `integration-worker` | `TF_DATA_DIR` | `/data`. |

Every variable is listed in [Environment variables](/docs/reference/environment-variables).

<Callout type="warn">
  If `ENCRYPTION_KEY` is unset, the app generates one and writes it to `/data/secrets.env`.
  In a cluster that is a trap unless `/data` is backed up and reliably shared: losing that
  volume makes the database — which holds only ciphertext — undecryptable. The app detects
  this and **refuses to boot** rather than orphaning your secrets. Put the key in a
  `Secret` from day one.
</Callout>

## First boot

There is no browser at first boot in most cluster workflows. Use
[headless seeding](/docs/deploy/headless): set `ADMIN_EMAIL`, `ADMIN_PASSWORD`, and
`LLM_API_KEY` together on `app`, and the instance seeds itself and skips the wizard.

## Ingress

Terminate TLS at the Ingress and route only to the `app` Service on port `8080`. Do not
publish `worker` or `integration-worker`; their HTTP servers are probe-only.

**Disable response buffering.** Chat streams over Server-Sent Events; a buffering ingress
holds every token until the turn completes and the UI looks frozen. On ingress-nginx:

```yaml
nginx.ingress.kubernetes.io/proxy-buffering: "off"
nginx.ingress.kubernetes.io/proxy-read-timeout: "3600"
```

## Backups

Back up PostgreSQL **and** the persistent storage behind `/data` and
`/opt/tulipfarm/soul`. `/data` holds the encryption key when you have not supplied one and
also holds auto-minted worker credentials; the soul holds your entire configuration unless
it is mirrored to a git remote (`SOUL_GIT_REMOTE_URL`). See
[Updating and rollback](/docs/deploy/updating).
