---
title: Deployment troubleshooting
description: Diagnose failed boots, unhealthy workers, stuck turns, integration ingress, login loops, and database extension errors.
---

Start with the service logs. The published Compose stack has three TulipFarm processes:

```bash
docker compose logs -f app
docker compose logs -f worker
docker compose logs -f integration-worker
```

`app` is the API, built web UI, and only migrator. `worker` executes every turn.
`integration-worker` handles Slack and GitHub ingress, sync, delivery, retries, and
reconciliation.

## `app` `/readyz` returns `503`

`/readyz` on `app` runs a datastore check. During first boot it can return `503` until
migrations finish; after that, check `docker compose logs -f app` for the real cause.
Common causes:

| Symptom | What to check |
| --- | --- |
| Connection refused, timeout, or SSL error | `DATABASE_URL`, security groups, SSL mode, and whether bundled `postgres` is healthy. |
| Migration error | The failing statement is in `app` logs. Fix the database problem, then restart `app`. |
| `vector` or `citext` failure | The database role cannot create the required extensions, or the provider has not allow-listed them. |

Migrations are forward-only and run only in `app`; neither worker applies schema changes.

## Workers refuse to boot below their schema floor

Both workers wait for `app` to become healthy and then check the database schema floor they
require. If either log says it is waiting for API migrations or refusing to start below a
schema version, do not scale the worker or bypass the check. Fix `app` first:

```bash
docker compose logs -f app
```

Then restart the worker that failed:

```bash
docker compose up -d worker integration-worker
```

## A chat turn never produces an answer

The API only submits the Run and streams persisted Run events. The `worker` executes the
turn. If the UI accepts a message but no answer appears:

1. Confirm `worker` is running and healthy.
2. Read `docker compose logs -f worker`.
3. Confirm `INTERNAL_API_URL=http://app:8080` and that the worker has a real
   `WORKER_API_CREDENTIAL`.
4. Confirm the `tulipfarm-data` volume is mounted read-only at `/data` in `worker`.

In the default Compose stack, `app` mints `/data/worker.env` on first boot and `worker`
reads it back. Losing `tulipfarm-data` removes that credential and can also remove the
encryption key.

## Slack or GitHub events never arrive

Ingress, sync, delivery, retries, and reconciliation run in `integration-worker`, not in
`app`. If Slack or GitHub setup looks correct but events do not arrive:

1. Confirm `integration-worker` is running and healthy.
2. Read `docker compose logs -f integration-worker`.
3. Confirm `INTERNAL_API_URL=http://app:8080` and that it has a real
   `INTEGRATION_WORKER_API_CREDENTIAL`.
4. Confirm `tulipfarm-data` is mounted read-only at `/data` so it can read
   `/data/integration-worker.env`.

## Login succeeds, then immediately disappears

`PUBLIC_URL` must be the exact origin users open, including the scheme. It drives CORS and
whether session cookies are marked `Secure`.

| You browse | Set |
| --- | --- |
| LAN HTTP | `PUBLIC_URL=http://<host-ip>:<HOST_PORT>` |
| Reverse proxy with TLS | `PUBLIC_URL=https://your-domain` |

After changing it, recreate the containers so every process sees the new environment.

## Missing `/data` volume

The `tulipfarm-data` volume is not optional. The `app` writes generated bootstrap secrets
and auto-minted worker credentials there; both workers read their credentials from it. If
`app` cannot persist generated secrets, it refuses to boot rather than create keys that
will disappear on restart.

If `/data` was lost after the instance stored secrets, restoring only PostgreSQL is not
enough. Restore `tulipfarm-data` or set `ENCRYPTION_KEY` back to the original value.
Without the original key, stored LLM keys and integration credentials are unrecoverable.

## Managed Postgres extension failures

TulipFarm requires both extensions:

```sql
CREATE EXTENSION IF NOT EXISTS vector;
CREATE EXTENSION IF NOT EXISTS citext;
```

The `app` runs those at boot. On managed providers, the extension usually must be enabled
or allow-listed by the provider before the application role can create it. If logs mention
permission denied, unknown extension, or `vector.control`, fix the provider setting or use
a role with permission, then restart `app`.
