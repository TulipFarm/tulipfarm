## Design and ownership

The document lifecycle, search/session orchestration and ranking, and
embedding job/cache/retry/dispatch algorithms move into `memory-core`.
The original Knowledge constructors retain their names, options, defaults,
and host transaction types and compose the moved implementations.

Core contexts are opaque type parameters: a core engine cannot read a
Postgres client, schema, storage version, or call `qualified()`.
`TenantRuntime` delegates to the original host runtime, retaining its
compatibility, deadline, transaction, and rollback behavior.
The host supplies the tenant ID and conversation capability separately.

`memory-postgres` implements typed document, session, embedding, lexical,
and vector operations. Each operation has explicit parameter types, not
an arbitrary SQL string or generic query-ID dispatcher. Existing row
layouts and engine-side Zod parsing remain intact so this extraction
does not alter validation, errors, or final authorization rechecks.
Schema and table prefix are explicit adapter configuration. Identifier
quoting remains pg's `escapeIdentifier`.

Membership, Files, task/conversation authority, provider reader selection,
availability checks, eligibility predicates, and embedding discovery
joins remain in Knowledge's host authorization adapters. Host migrations,
foreign keys, provider synchronization, project features, and Temporal
remain unchanged. This milestone does not pull M7's provider work forward.

Recommendation invalidation/change hooks and error constructors are
injected unchanged. External callbacks retain bare invocation. Repository
objects are cached by transaction context, never by pooled connection,
so tenants sharing a connection cannot share configured schema state.

The document schemas that require host provenance use the original host
dependency schema as an explicit input. Pure schemas, error classes, and
identifier helpers move with the engines and forward from their old paths.
The public embedding contract definitions also forward unchanged.

## M5 follow-up: UUID normalization

The user cleared M5's security review with no exploitable findings:
SQL text/parameters, access-check order, transaction scoping, and lease
fencing were verified equivalent to `3d5f606`. The review found a
non-security compatibility error: the moved internal UUID schema used
plain `z.uuid()`, while Access's original UUID schema also lowercased
the parsed value.

The shared internal core schema now uses the exact former lowercase
transform, without a host import. Internal citations explicitly override
their five UUID fields with that schema: their new browser-contract base
never normalized case, while the original internal Access dependency did.
The earlier browser contracts and non-UUID identifiers (`nativeId`,
`profileId`) retain their original case-preserving behavior.

Five new tests cover the shared UUID schema, every moved document and
embedding UUID field, internal versus browser citations, and uppercase
workspace IDs reaching both document and embedding transaction runtimes
in lowercase. The initial focused run had 18 tests, 14 passes and four
failures at the exact missing-normalization assertions; the fixed run
passes all 18. See `M5-uuid-red.tap` and `M5-uuid-green.tap`.

All 36 scoped build/typecheck tasks and lint passed. Affected unit suites
passed: core 238/238, Postgres 8/8, Knowledge 64/64. The entire Knowledge
integration suite completed serially: 28 files, 257 tests, 254 passes,
the same three known failures, no skips or cancellations. All strict
comparisons pass; no new comparison exception was added. Original M5
receipts remain byte-identical; follow-up receipts use `M5-uuid-*`.
`M5-uuid-final-counts.json` records the final integration totals.

Two unexpected integration results were investigated under standing authority:

- Google repairs initially failed at `google-repairs.integration.mjs:102`
  (`assert.ok(work)`, two subtests) and `:406` (`0 !== 1`), plus its
  parent test. Five current and five detached `99c5e99` reruns all passed
  all 15 tests. Its cause is unproved and it has no accepted exception.
  An initial baseline setup run could not import Workspaces' built
  `table-migrations.js`; that setup receipt is preserved separately,
  the missing dependency was built, and all five baseline tests then ran.
- Hybrid search hit SQLSTATE `23514` on
  `tf_knowledge_search_sessions_check`. Three of five current runs
  failed; both remaining current runs and all five baseline runs passed.
  The raw PostgreSQL error rows prove an environment clock mismatch:
  expiry exceeded database `created_at + interval '5 minutes'` by
  5.510, 5.573, 6.527, and 0.312 ms. For example, current run 2 records
  `created_at=2026-10-21 07:28:57.641427+00` and
  `expires_at=2026-10-21 07:33:57.647+00`.
  Search computes expiry with the app clock; PostgreSQL independently
  checks its own clock. Those calculations, SQL, and constraint are
  unchanged by the UUID fix, and even an empty keyword-only session
  exhibits the failure. Restarted only the owned PostgreSQL service and
  reran the strict check successfully. No SQL, clock injection,
  constraint, timeout, existing test, or tolerated-failure rule changed.
